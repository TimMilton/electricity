# Електрооблік будинку

Вебзастосунок для обліку показників квартирних лічильників, нарахувань за електроенергію, додаткових внесків, спільного депозиту будинку та оплат мешканців. Інтерфейс українською, валюта — гривня, часовий пояс — Europe/Kyiv.

**Стек:** Next.js 16 (App Router, Server Actions) · TypeScript (strict) · Tailwind CSS 4 · компоненти у стилі shadcn/ui на Radix · Supabase (Auth, PostgreSQL, Storage) · Zod · React Hook Form · Vitest · Playwright.

## Запуск у Docker

Увесь застосунок разом із власним Supabase (база, авторизація, сховище квитанцій) запускається однією командою. Хмарний акаунт Supabase не потрібен.

**Потрібно:** Docker з Compose v2 (Docker Desktop на Windows/macOS або Docker Engine на Linux), ≈2 ГБ вільної пам'яті.

### Перший запуск на своєму комп'ютері

```bash
# 1. Створити .env з випадковими паролями й ключами
node docker/init-env.mjs
#    без встановленого Node:
#    docker run --rm -v "$PWD:/w" -w /w node:22-alpine node docker/init-env.mjs
#    (Windows PowerShell: замініть "$PWD:/w" на "${PWD}:/w")

# 2. Зібрати й запустити (перший раз — кілька хвилин)
docker compose up -d --build

# 3. Створити адміністратора (пароль буде запитано)
docker compose exec app node scripts/create-admin.mjs --email you@example.com --surname Прізвище
```

Відкрийте **http://localhost:8080** і увійдіть як адміністратор. Далі — [Перше налаштування застосунку](#перше-налаштування-застосунку).

Потім у розділі «Квартири» додайте квартири й видайте коди доступу. Мешканець входить за **номером квартири та кодом** — без пошти й реєстрації. Код діє постійно; змінити його може лише адміністратор.

### Що запускається

| Контейнер | Призначення |
|---|---|
| `gateway` | Caddy — єдина точка входу; на сервері з доменом сам налаштовує HTTPS |
| `app` | вебзастосунок |
| `db` | PostgreSQL (образ Supabase) — дані у томі `db-data` |
| `auth` | Supabase Auth — облікові записи квартир і адміністраторів |
| `rest` | PostgREST — доступ застосунку до бази з RLS |
| `storage` | Supabase Storage — квитанції у томі `storage-data` |
| `migrate` | при кожному запуску застосовує нові міграції й завершується |
| `cron` | щоденна задача: створює розрахунковий період, оновлює статуси |

Назовні відкрито лише шлюз. API бази даних і адмін-API авторизації доступні тільки серверу застосунку всередині мережі Docker; браузер бачить лише сторінки застосунку та підписані посилання на квитанції.

### Сервер з доменом і HTTPS

1. Спрямуйте DNS-запис (A/AAAA) домену на сервер, відкрийте порти 80 і 443.
2. На сервері:
   ```bash
   git clone <репозиторій> elektrooblik && cd elektrooblik
   node docker/init-env.mjs --domain elektro.example.com
   ```
3. `docker compose up -d --build` і створіть адміністратора, як вище. Сертифікат Let's Encrypt Caddy отримає автоматично.

### Щоденне керування

```bash
docker compose ps                     # стан контейнерів
docker compose logs -f app            # журнал застосунку (або auth, storage, migrate…)
docker compose restart app            # перезапуск
docker compose down                   # зупинити (дані зберігаються в томах)
git pull && docker compose up -d --build   # оновлення: нові міграції застосуються автоматично
scripts/docker-backup.sh              # резервна копія (див. нижче)
```

> **Не виконуйте `docker compose down -v`** — прапорець `-v` видаляє томи з базою й квитанціями.

### Лише застосунок у Docker + Supabase Cloud

Якщо база в Supabase Cloud, достатньо одного контейнера:

```bash
docker build -t elektrooblik .
docker run -d --name elektrooblik -p 3000:3000 --restart unless-stopped \
  -e SUPABASE_URL=https://YOUR-PROJECT.supabase.co \
  -e SUPABASE_ANON_KEY=... -e SUPABASE_SERVICE_ROLE_KEY=... \
  -e SITE_URL=https://elektro.example.com -e CRON_SECRET=... \
  elektrooblik
```

Образ не містить жодних адрес чи ключів — усе передається під час запуску, тож один образ підходить для будь-якого середовища. Міграції застосуйте до хмарного проєкту, як описано в [Налаштування Supabase Cloud](#налаштування-supabase-cloud); щоденну задачу викликайте планувальником: `curl -H "Authorization: Bearer $CRON_SECRET" https://.../api/cron/periods`.

### Якщо щось не так

- **Образ не завантажується** (`manifest unknown`): версії образів Supabase задано у `.env.docker.example`. Розкоментуйте відповідний рядок у `.env` і вкажіть актуальну версію з [офіційного docker-compose Supabase](https://github.com/supabase/supabase/blob/master/docker/docker-compose.yml).
- **`app` не стартує:** перегляньте `docker compose logs migrate` — застосунок запускається лише після успішних міграцій.
- **Порт 8080 зайнятий:** `node docker/init-env.mjs --force --port 9000` (лише до першого запуску: `--force` створює нові паролі) або змініть `HTTP_PORT` і `PUBLIC_URL` у `.env`.
- **Перевірка стану:** `curl http://localhost:8080/api/health?deep=1` має повернути `{"ok":true,"supabase":"up"}`.

## Як влаштовано

**База даних — джерело істини.** Уся фінансова логіка (розрахунок споживання та сум, статуси платежів, депозит, розбіжності) реалізована у функціях PostgreSQL (`SECURITY DEFINER`) і виконується в транзакціях. Користувачі мають лише право `SELECT` (обмежене RLS); будь-яка зміна проходить через функцію, яка перевіряє роль, власника квартири, стан періоду та записує подію в журнал змін. Браузер показує попередній розрахунок, але остаточні суми рахує сервер.

**Гроші без float.** У базі — `numeric` (гроші `numeric(12,2)`, показники `numeric(12,2)`, тариф `numeric(10,4)`), округлення `round(x, 2)`. У TypeScript — `BigInt` у мінімальних одиницях з тим самим правилом округлення («половина від нуля»).

**Окремий облік сутностей:**

| Сутність | Таблиця | Що зберігає |
|---|---|---|
| Індивідуальне споживання | `meter_readings` | показники, зафіксований тариф, сума за електроенергію |
| Внески мешканця | `additional_charges` | депозит, освітлення під'їзду, інші — окремими рядками |
| Платіж | `payments` + `payment_events` | зафіксовані суми, статус, усі спроби та рішення |
| Квитанції | `receipts` + приватний бакет `receipts` | файли, прив'язані до платежу і спроби |
| Депозит будинку | `deposit_ledger` | незмінний журнал операцій зі знаком; баланс = сума |
| Загальний лічильник | `common_meter_readings` | показники лічильника будинку |
| Розбіжності | `reconciliation_records` | розрахунок, статус перевірки, пояснення |
| Журнал змін | `audit_logs` | автор, роль, дія, було/стало, причина |

**Ключові правила:**
- Депозитний внесок потрапляє в депозит лише при підтвердженні платежу; повторне підтвердження нічого не змінює (ідемпотентність + унікальний індекс).
- Розбіжність лише розраховується; депозит використовується тільки рішенням адміністратора після перевірки, з підставою, у межах балансу.
- Від'ємна розбіжність не зменшує депозит; неповні дані позначаються «Неповні дані».
- Тариф фіксується в показнику під час першого подання; новий тариф не змінює минулих нарахувань.
- Виправлення старого показника, що впливає на наступні місяці, вимагає явного підтвердження і не перераховує їх непомітно.
- Журнал депозиту, журнал змін, історія платежів і квитанції захищені від зміни/видалення тригерами (навіть для власника БД).

## Локальна розробка без Docker

Потрібно: Node.js ≥ 20.9 і Supabase (Supabase CLI з Docker або хмарний проєкт).

```bash
npm install
cp .env.example .env.local        # заповніть значення

# варіант А — локальний Supabase (потрібен Docker)
npx supabase start                # застосує міграції з supabase/migrations
npx supabase status               # API URL → SUPABASE_URL, anon key → SUPABASE_ANON_KEY,
                                  # service_role key → SUPABASE_SERVICE_ROLE_KEY (у .env.local)

# варіант Б — хмарний проєкт: див. «Налаштування Supabase»

npm run create-admin -- --email you@example.com --surname Прізвище
npm run dev                       # http://localhost:3000
```

> Змінні читаються під час запуску (не вбудовуються у збірку). Старі назви `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` теж підтримуються.

### Попередній перегляд без бази

Щоб просто подивитися на інтерфейс без Supabase і входу:

```bash
npm install
npm run dev
# відкрийте http://localhost:3000/preview
```

Сторінка `/preview` показує головну мешканця, внесення показників, оплату, список мешканців і огляд адміністратора на вигаданих даних. Кнопки, що зберігають дані, там не працюють. У production-збірці сторінка вимкнена (увімкнути: `ENABLE_PREVIEW=1`).

## Налаштування Supabase Cloud

> Для запуску в Docker цей розділ не потрібен — стек налаштовується автоматично.

1. **Створіть проєкт** на supabase.com (регіон — найближчий, напр. Frankfurt). Збережіть пароль бази.
2. **Застосуйте міграції** (по черзі, у порядку номерів):
   - через CLI: `npx supabase link --project-ref <ref>` → `npx supabase db push`;
   - або вручну: SQL Editor → вставити й виконати кожен файл із `supabase/migrations/`.
3. **Ключі:** Project Settings → API → скопіюйте URL, publishable/anon key і service_role/secret key у змінні `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (`.env.example`).
4. **Storage:** міграція створює приватний бакет `receipts` і політики доступу. Перевірте в Storage → Buckets, що бакет **Private**. Політики: читання — власна квартира або адміністратор; запис — лише у теку власного платежу; оновлення/видалення — заборонено.
5. **RLS:** після міграцій у Database → Tables усі таблиці `public` мають позначку RLS enabled. Database → Advisors (Security) не повинен показувати таблиць без RLS.
6. **Auth → Sign In / Providers:** вимкніть **Allow new users to sign up** — облікові записи квартир створює сам застосунок (сервісним ключем), відкрита реєстрація не потрібна. Налаштування пошти (Confirm email, SMTP, Site URL) застосунок не використовує: листів він не надсилає.

## Перше налаштування застосунку

1. **Перший адміністратор** (самостійно стати адміністратором неможливо):
   ```bash
   docker compose exec app node scripts/create-admin.mjs --email admin@example.com --surname Прізвище   # Docker
   npm run create-admin -- --email admin@example.com --surname Прізвище                                # без Docker
   ```
   Альтернатива без Node: створіть користувача в Auth → Users і виконайте в SQL Editor
   `select public.bootstrap_admin('<uuid користувача>', 'Прізвище');`
2. **Квартири:** «Квартири» → «Додати квартиру» або імпорт CSV (`номер;прізвище;початковий показник`). Початковий показник потрібен для першого розрахунку; без нього мешканець вкаже його сам під час першого подання.
3. **Коди доступу:** «Видати коди всім квартирам без доступу» → завантажте CSV і передайте коди мешканцям особисто (або «Видати код» у рядку квартири). Мешканець входить за номером квартири та кодом. Код діє постійно й показується лише в момент видачі; якщо мешканець його загубив — «Змінити код» (старий одразу перестає діяти). Коди зберігаються лише як хеш паролю в Supabase Auth.
4. **Тариф:** «Періоди й тарифи» → «Встановити тариф» (грн/кВт·год, дата початку дії). Застосунок не містить жодного тарифу за замовчуванням.
5. **Період:** «Новий період» — місяць показників і вікно приймання (за Києвом). Типові дні (напр. 1–5 число) задаються в налаштуваннях. За наявності `CRON_SECRET` щоденна задача сама створює період поточного місяця, якщо адміністратор його не створив.
6. **Конверт:** «Налаштування» → «Посилання на спільний конверт» (лише `https://`).
7. Перевірте роботу через «Переглянути як мешканець».

## Розгортання на Vercel

1. Імпортуйте репозиторій у Vercel (Framework: Next.js).
2. Environment Variables (Production і Preview): `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SITE_URL` (https-адреса), `CRON_SECRET`.
3. Deploy. `vercel.json` реєструє щоденний Cron `/api/cron/periods` (00:05 UTC).

Інший хостинг: Docker-образ (див. [Лише застосунок у Docker](#лише-застосунок-у-docker--supabase-cloud)) або `npm run build && npm run start:standalone` (Node ≥ 20.9). Для кількох інстансів задайте спільний `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`; cron викликайте зовнішнім планувальником з заголовком `Authorization: Bearer $CRON_SECRET`.

## Резервне копіювання та відновлення

### Docker

```bash
scripts/docker-backup.sh                              # → backups/РРРР-ММ-ДД_ГГХХ/
scripts/docker-restore.sh backups/2026-10-17_0330     # замінює поточні дані копією
```

Копія створюється без зупинки й містить: дані бази (облікові записи, квартири, показники, платежі, депозит, журнали), файли квитанцій і копію `.env`. **Зберігайте копії поза сервером** (інший диск, хмара): копія на тому самому диску не врятує від його поломки. Для щоденних копій — рядок для cron наведено на початку `scripts/docker-backup.sh`.

Відновлення на новому сервері: скопіюйте проєкт, покладіть `env.backup` з копії як `.env`, `docker compose up -d --build`, потім `scripts/docker-restore.sh <каталог>`. Версії образів мають збігатися з тими, що були під час створення копії.

### Supabase Cloud

**Автоматично:** платні плани Supabase мають щоденні бекапи (Database → Backups) і Point-in-Time Recovery як опцію. На безкоштовному плані бекапи робіть самостійно.

**Ручний бекап бази** (connection string — Project Settings → Database):
```bash
pg_dump "$SUPABASE_DB_URL" --schema=public --format=custom --file=elektrooblik-$(date +%F).dump
# окремо: користувачі Auth (для повного відновлення)
pg_dump "$SUPABASE_DB_URL" --schema=auth --data-only --format=custom --file=auth-$(date +%F).dump
```
**Бекап квитанцій:** Storage → `receipts` (або `supabase storage cp -r ss:///receipts ./receipts-backup --experimental`).

**Відновлення** у новий проєкт: застосуйте міграції → `pg_restore --data-only --disable-triggers -d "$NEW_DB_URL" auth-….dump` → те саме для public → завантажте файли квитанцій у бакет `receipts` зі збереженням шляхів. `--disable-triggers` потрібен, бо журнали захищені тригерами незмінності. Після відновлення перевірте баланс депозиту в адмін-панелі та вибірково — кілька квитанцій.

Рекомендовано: щомісячний CSV-експорт («Експорт») після закриття місяця як додаткова людиночитна копія.

## Безпека

- Supabase Auth; облікові записи квартир створює лише сервер від імені адміністратора; відкрита реєстрація вимкнена. Роль адміністратора не можна отримати запитом до профілю (немає прав на запис + тригер).
- RLS на всіх таблицях; `anon` не має доступу до даних; хеш коду та службові поля квартир приховані на рівні колонок.
- Сервісний ключ використовується лише на сервері (`server-only`), ніколи в браузері.
- Квитанції: приватний бакет, шляхи видає сервер, тип перевіряється за вмістом файлу, перегляд — підписаними посиланнями на 5 хвилин.
- Zod на сервері для всіх дій; параметризовані виклики (без конкатенації SQL); React екранує вивід; суворі заголовки (CSP, `X-Frame-Options: DENY`, `nosniff`); CSV захищено від формульних ін'єкцій.
- Обмеження спроб входу: за IP-адресою та окремо за номером квартири (таблиця `rate_limits`). Код доступу — 10 випадкових символів (≈10¹⁵ варіантів), тож підбір неможливий.
- Ідемпотентне підтвердження платежів, блокування рядків `FOR UPDATE`, advisory lock для операцій депозиту.
- Повідомлення про невдалий вхід однакові для неіснуючої квартири й невірного коду і не розкривають даних мешканців.

## Відомі обмеження

- Інтеграцію з реальним Supabase (GoTrue/PostgREST/Storage) у середовищі розробки не запускали: e2e-сценарій `full-flow` написаний, але потребує `supabase start` або тестового проєкту. База даних, RLS і бізнес-логіка перевірені на реальному PostgreSQL 16.
- Docker-стек у середовищі розробки не запускався: реєстри образів там недоступні. Перевірено окремо: автономна збірка застосунку з налаштуваннями під час запуску, валідність `docker-compose.yml`, скрипт міграцій (очікування сервісів, повторний запуск, відкат невдалої міграції), цикл резервне копіювання → очищення → відновлення на PostgreSQL, генерація ключів JWT. Перший `docker compose up` варто зробити на тестовій машині й пройти сценарій видачі коду, входу мешканця та оплати.
- Версії образів Supabase в `docker-compose.yml` зафіксовані на відомих на момент написання; якщо якийсь тег недоступний, змініть його в `.env` (див. «Якщо щось не так»).
- `supabase/config.toml` мінімальний; якщо ваша версія CLI скаржиться на ключі, виконайте `npx supabase init` і перенесіть міграції.
- Сповіщень мешканцям (email/Telegram) про відхилення чи підтвердження оплати немає — статус видно в застосунку.
- Розбіжність порівнює загальний лічильник із сумою показників того самого розрахункового місяця; якщо мешканці знімають показники в різні дні, різниця частково пояснюється датами зняття.
- Тариф для періоду визначається на дату початку місяця; зміна тарифу посеред місяця застосовується з наступного періоду.
- Залежності `eslint-config-next` мають попередження `npm audit` (dev-only, не потрапляють у збірку).
